Development of VAS Pad

A Canvas-Based Visual Analog Scale Web Application with an Explicit Unanswered State


ICISIP 2026

Naruki Shirahama, Naofumi Nakaya, Satoshi Watanabe
A manual-first talk: from system development to practical dissemination

Hello everyone. This presentation is based on our ICISIP 2026 paper, "Development of VAS Pad: A Canvas-Based Visual Analog Scale Web Application with an Explicit Unanswered State." However, I will not simply repeat the paper section by section. The system is already described in the paper, so today I will emphasize how VAS Pad can be used and disseminated as a practical platform. The central technical idea is simple: before a respondent answers, a VAS should not display an answer position. Around that idea, VAS Pad provides respondent screens, administrator tools, multilingual content, JSON settings, CSV export, and PWA support. My goal is that you understand not only what we built, but also how a researcher or instructor can actually run a VAS study with it.

The submitted paper establishes the technical and research motivation. For this conference presentation, I want to shift the emphasis toward adoption. A tool becomes valuable when other people can understand its workflow, configure experiments, avoid common mistakes, and export data in a usable form. That is why the user manual is central to this talk. The manual explains what respondents see, what administrators must configure, and what checks are necessary before data collection. In other words, the paper gives the scholarly basis, and the manual turns the system into something that can spread to laboratories, classrooms, and collaborative projects.

The measurement-interface problem

HTML slider

VAS Pad Canvas

The marker appears only after action.

Convenient implementation is not always measurement-equivalent implementation.

The motivation begins with a small interface detail. In a paper-based VAS, the respondent sees a line with semantic anchors, but no response position exists until the respondent makes a mark. In many web questionnaires, this line is replaced with an HTML range slider. That is convenient, but it changes the interface. A slider normally has a visible thumb and a current value even before the respondent has formed an answer. In particular, a midpoint default can become an unintended cue. VAS Pad was designed to avoid that cue. It uses Canvas to draw the line, stores the unanswered state as null, and draws the response marker only after a click, tap, or drag operation. This is the foundation of the entire system.

Respondent-side stimulus and VAS screen

The most important data-model decision is the distinction between null and zero. If a VAS value is stored as zero before the respondent acts, we cannot distinguish a missing response from a valid answer at the left endpoint. VAS Pad keeps the value as null until the respondent interacts with the line. After the interaction, the position on the line segment is converted to a value from zero to one hundred. Respondents can adjust the position by dragging. They also cannot move forward while a required VAS question remains unanswered. This implementation supports both visual neutrality and data integrity. The interface remains close to paper VAS before the response, and the exported data remains easy to analyze after the response.

The manual presents VAS Pad as a complete respondent experience, not only as an input widget.

For dissemination, the respondent experience is just as important as the VAS component itself. A participant opens the response URL, reviews the research information, and chooses whether to participate. If they agree, they read the response instructions. In the example shown in the manual, the instructions specify the target person, the meaning of the endpoints, and how to answer confidence. Then the respondent views a stimulus and answers multiple VAS questions. After all stimuli are completed, the final screen appears, and the response is submitted only when the respondent selects the submit button. The completion screen confirms that submission succeeded. This flow is useful because it reduces ambiguity for participants and gives researchers a predictable structure for web-based VAS studies.

Research ethics are built into the workflow

  • Consent gate: declining participation stops the survey.
  • Comprehension check: misunderstanding can be detected before responses.
  • Required VAS answers: accidental missing values are reduced before submission.
  • Data-policy transparency: consent text should match the research protocol and platform use.

VAS Pad is not only a convenient survey screen. It also provides workflow elements that are important in human-participant research. The consent screen can describe study purpose, eligibility, voluntary participation, withdrawal, personal information, response data, and contact information. If a person does not consent, the survey does not begin. The comprehension check helps confirm that the participant understands the instructions before answering. If the answer is wrong, the system can show an explanation and ask the participant to review the relevant point. At the same time, VAS Pad does not remove the researcher's responsibility. For example, anonymous IDs, Firebase operations, and YouTube stimuli may still involve platform-side records or third-party services. Therefore, consent wording and data-management policies must be carefully aligned with the actual study.

Supported locales in the manual: Japanese, English, Simplified Chinese, Traditional Chinese, and Korean.

A major dissemination feature is multilingual support. VAS Pad separates the interface language from the survey language. The interface language affects shared navigation, the administrator page, and general system elements. The survey language affects experiment-specific content such as the research information, instructions, comprehension-check text, stimulus content, VAS labels, and end messages. This separation is useful when a researcher wants the system interface in one language but needs respondents to answer a survey in another language.

The administrator workflow is also important for adoption. A single deployment of VAS Pad can contain multiple experiments, and each experiment has its own settings, language content, and response data. When creating a new experiment, the administrator enters a clear title and a slug. Administrators can then switch which experiment they are editing from the management screen.

Each experiment has its own response URL

Default experiment:       https://vaspad.web.app/
Other experiment:         https://vaspad.web.app/{slug}
Example slug:             text-presentation
Example response URL:     https://vaspad.web.app/text-presentation
Do not distribute only the top-level URL when the intended experiment uses a slug.

The slug entered when an experiment is created becomes part of the respondent URL. The default experiment uses the top-level URL, but other experiments use the top-level URL followed by the slug. Switching the experiment on the administrator page changes what you are editing; it does not automatically redirect the public top-level URL. This detail is easy to overlook, so the manual emphasizes it strongly. For real data collection, distributing the correct response URL is a basic but critical operational requirement.

The administrator edits structure once, then applies common VAS questions across multiple stimuli.

VAS Pad is designed to reduce the amount of one-off survey programming required for VAS studies. The administrator can edit the consent screen, shared instructions, comprehension check, stimulus items, VAS questions, decline end message, and final message from the admin page. Stimuli can be text, YouTube videos, or images. Text stimuli support formatted content, and common VAS questions can be applied to every stimulus item. This is especially useful when the same emotions, impressions, or confidence ratings must be collected repeatedly across several materials. The manual also gives practical authoring advice: do not reverse endpoint meanings accidentally, avoid incomplete translations, and make sure the instructions are consistent with every VAS label. These are small details, but they directly affect data quality.

For research use, reproducibility and data handling matter. VAS Pad allows settings to be exported and imported as JSON. This supports backup, duplication of experiments, version management, and collaborative review. It also makes generative-AI-assisted editing or translation easier, because the structure can be represented explicitly. However, JSON import is not the same as validation. The manual warns that the administrator must review imported settings and then save them before they become active. After data collection, responses are downloaded as CSV for the currently selected experiment. This is important: response data are separated by experiment. The administrator must select the correct experiment before downloading. In practice, the JSON and CSV workflow connects questionnaire design, operation, and analysis.

VAS Pad supports comparison between model behavior and human subjective evaluation.

The paper describes two use-case directions. The first is research on emotional-intelligence evaluation of large language models, especially the EQ-Fuzzy line of work. In this context, human VAS data are needed to compare model behavior with human subjective evaluation. VAS Pad can present literary texts or conversational materials and collect fine-grained affective intensity ratings and confidence while supporting consent, comprehension checks, anonymous response management, and CSV export.

The second direction is education. In the third-year data science project exercise at Shimonoseki City University, students used VAS Pad to configure web experiments, collect responses, download CSV data, analyze results, visualize data, and write reports. This classroom use is not presented as a learning-outcome evaluation. Rather, it shows that the platform is practical enough to support a complete data-science project cycle and can serve as reusable infrastructure for subjective-evaluation practice.

Operating checklist for adopters

  1. Create or select the correct experiment.
  2. Set editing locale, default locale, and published locales.
  3. Edit consent, instructions, and comprehension check.
  4. Register stimuli and shared VAS questions.
  5. Select Save, then distribute the correct slug URL.
  6. Export JSON before operation; download CSV after collection.
<div class="takeaway">Most failures are operational: wrong experiment, wrong language, unsaved edits, or wrong response URL.</div>
The Save button stores all current edits for the selected experiment.

The manual ends with a recommended operating procedure, and I think this is one of the most useful parts for dissemination. Before launching an experiment, the administrator should confirm the experiment title and slug, configure language settings, edit the research information, shared instructions, comprehension check, stimuli, VAS questions, final messages, display fields, and design. Then the settings must be saved. After saving, the administrator should distribute the correct response URL, preferably with the experiment slug when the experiment is not the default one. JSON backup should be downloaded when appropriate. After data collection, the administrator should again verify the selected experiment and download the CSV. Many practical mistakes are not programming errors. They are workflow errors, and the manual is designed to reduce them.

VAS Pad is a small interface correction with a large operational goal: reliable VAS surveys that other people can actually run.

To close, I want to emphasize both the current contribution and the future boundary. VAS Pad already provides a Canvas-based VAS input that avoids an initial marker, together with the surrounding functions needed for research and education: consent, instructions, comprehension checks, multiple stimuli, multilingual content, JSON settings, CSV response download, Firebase-based administration, and PWA support. The user manual is an important dissemination step because it explains how respondents and administrators should actually use the system. At the same time, this is still a system-development report. We still need stronger accessibility design, stronger validation and preview for imported settings, operational safeguards, and empirical comparison among paper VAS, ordinary sliders, and VAS Pad.
